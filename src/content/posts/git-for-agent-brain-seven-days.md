上一篇[《Agent 为什么也需要一套自己的 Git》](/posts/agent-native-git/)讲的是一个判断：会长期自我改变的 AI agent，需要版本管理。当时它只是一个想法。

现在它跑了七天，76 个 commit，救过火，也摔过跤。这篇把整个事情从头讲到尾：agent 是什么、数据原来怎么存、Git 为什么挂得上去、我们具体做了什么、收益和代价各是什么。

## 先交代主角：我们用的 Agent 是什么

说的是 [Hermes](https://hermes-agent.nousresearch.com)，Nous Research 开的源，一个跑在我们自己电脑上的 AI 助理，不是网页里的聊天机器人。我们团队用它管理日常工作流：它每天凌晨扫描团队群聊和会议纪要，把 Yinsen 派出去的任务建档、跟进、到期催办；每天早上八点把当天日程和待办做成卡片发到飞书；它写周报、发邀请邮件、盯开源仓库、跑定时流水线，也会在我们提需求后自己去改自己的"工作手册"。

关键在最后半句。这个系统不是一段固定的 prompt 加上一个模型——它有一个会生长的目录：

- **技能（Skills）**：两百多个 Markdown 文件，每个是一种工作方法的说明书。"怎么给 GitHub 贡献者发邀请邮件""怎么做飞书文档的块级编辑"，都是它自己写、自己改的
- **记忆（Memory）**：跨会话持久的事实清单。"对外称呼用什么""哪些系统谁是权威源"
- **人格与规则**：SOUL.md 定义它是谁，配置目录里是各个自动化流程的提示词与参数
- **脚本与定时任务**：几百行 Python、shell，加一张 cron 表，驱动它每天自动干活

这些东西合起来，就是这个 agent 的"大脑"。它们全部是**纯文本文件**，放在它家目录（`~/.hermes`）下。这一条性质，是整个故事的前提。

## 它原生是怎么存数据的（认真看过源码之后）

先破一个容易的误解：Hermes 不是一个"SQLite 程序"。它的家目录里其实是两套东西共存。

**第一套：运行事实，活在 SQLite 里。** 一个 1.1 GB 的 `state.db`，三十来张表：每个会话的元数据、每条消息、工具调用记录、token 用量、全文检索索引、定时任务的执行账本、上下文压缩时父子会话的谱系、还有跨进程的租约锁。这些东西有严格的关联语义——一条消息属于哪个会话、一次工具调用和它的结果怎么配对、压缩产生的子会话从哪个父会话发布——所以官方给了三样配套保护：升级前的自动快照（`state-snapshots/`，实测三份里最新的一份因为 1 GiB 上限跳过了大数据库文件）、`hermes backup` 的完整 ZIP（对数据库走 SQLite 在线备份 API，保证拷出来的是事务一致的副本而不是半写状态）、以及恢复时的数据库专用路径（避免替换文件后老连接还在写旧对象）。这套东西 Git 帮不上忙，后面细说。

**第二套：可编辑资产，就是散装文件。** 上面说的技能、记忆、人格、脚本，没有任何索引数据库管理它们——技能是运行时扫描目录发现的，记忆是启动时读进来的 Markdown。官方对它们的保护手段是三种"快照"：完整备份 ZIP 会捎上它们，技能整理器运行前会 tar 一份技能树，还有一个默认关闭的 Checkpoint 功能（有意思的是，那个功能的实现本身就是一个影子 Git 库）。

**原生机制真正缺的是什么？不是"没有副本"，是副本不构成版本协议。** ZIP 和 tar 回答"某个时刻保存了什么"；版本管理还要回答"相对哪一版改了什么、为什么改、只想退这一个文件怎么办、两台机器各自改了怎么合"。官方 issue 区里有一条提"技能写入即提交"的讨论至今没有落地——这个需求是真实存在的，官方也承认，只是还没做。

## Git 为什么能无痛挂上去

这是被问最多的问题。一个跑着的产品，加个 `.git` 就完事了，不用改一行代码、不用停服务——凭什么？

先说一个不成立的流行答案："因为 agent 的数据是纯文本"。文本只是表面理由。GitHub 上多的是被文本折磨的仓库：一个两兆的单行 JSON，diff 完全不可读，文本性帮不了它。

我们从源码里核对出 Hermes 满足的，是另外几个更硬的条件：

**一、这些文件是"输入"，不是"状态"。** 技能、提示词、规则，是 agent 下次工作时读取的声明；消息、路由、租约，是它工作产生的事实。声明可以版本化，事实要另交备份协议。判断哪些文件进 Git，本质是回答"这是输入还是状态"。

**二、读取路径是"文件即权威"。** agent 每次加载技能，读的就是磁盘上那个文件的当前内容。Git 切换文件版本，不需要通知任何缓存、任何索引、任何服务。（细节诚实地说：有发现缓存，三十秒 TTL；有安装来源的清单文件；记忆在会话里是快照冻结的，旧会话不会倒退。但这些是刷新边界，不是"必须走官方 API 才认"的一致性协议——文件仍是唯一的真源。）

**三、文件的变更频率和它的历史价值是匹配的。** 技能一个月改几次，每次改动都是值得说明的决策；会话数据库一秒钟写十行，每行都没有单独留史的意义。Git 的粒度天然适合前者、天然不适合后者。

**四、一个文件（目录）大致对应一个概念。** 一个技能目录就是一种能力，一条记忆文件就是一册事实。改了什么、为什么改、退哪一条，都能按语义单元操作。

所以准确的说法是：**当系统的行为由文件型声明驱动、运行事实另有可靠存储、且声明的修改低频而有意义时，外挂版本层就是自然设计。**Hermes 恰好三条全中。这跟"它是不是 AI"关系不大——dotfiles 十年前就是这么管理 Linux 配置的。Agent 带来的新东西是放大器：它自己会改这些文件，改得比人快、比人多，七天的变更密度（76 commit）比大多数人的 dotfiles 仓库一年都高。"谁改的、为什么改、改坏了怎么退"这个问题，从理论担忧变成了每天的实际需求。

## 我们具体做了什么（全部操作）

没有什么平台，就是三步。

**第一步，`git init`，然后划边界。** `.gitignore` 是这个方案里最重要的一份文件，比所有 commit 都重要。三条线：

- 资产进库：skills/、记忆、人格文件、脚本、配置里的提示词与参数——共 2113 个文件，九成是技能
- 状态不进库：state.db 及 WAL、日志、缓存、快照目录、会话导出——那是 SQLite 协议的地盘
- 凭据死都不进：密钥文件、登录态、token——排除规则只是第一道，还要配内容扫描（这条是我们摔了跤之后补的，见下文）

**第二步，纪律。** 改任何资产前后各提交一次；commit message 写人话（"追问一律改用 bot 身份（Yinsen 09-04 指正）"这种）；每天凌晨的自动化任务收尾时把整包资产变更记一次快照 commit——机器产生的改动也要有人类的阅读入口。

**第三步，推到一个私有远端，然后在仓库根目录放一份 README。** 那份 README 是写给"未来接手这个目录的任何人或任何 AI"看的：这是什么仓库、为什么存在、恢复的三步命令、哪些文件永远不该进来、日常纪律是什么。这一条看起来最虚，七天后我们认为它最值——因为接手这套系统的第一候选，就是一台新机器上一个全新安装的 agent 自己。

配套的自动化两件：一个每天六点的健康检查（补丁完整性、数据单一来源扫描、新文件敏感内容扫描，红了发到飞书）；一个升级前的钩子（把定制补丁的恢复材料核对一遍）。这两个本身也踩出事过，下面讲。

## 七天战果：救火记

**54 秒的恢复。** 9 月 4 日官方升级，把代码仓库重置到上游，我们打在飞书适配层的两个定制补丁没了。因为补丁是以 commit 存在的：reflog 找回哈希，两条 `cherry-pick`，从 reset 到补丁回来，reflog 时间戳相差 54 秒。诚实说明两个边界：这是 reflog 上的窗口，不等于整个恢复流程只花 54 秒（发现、验证、重启服务都在窗口之外）；而且救回源码的是代码仓库自己的 Git——外层数据仓库的贡献，是把"该用哪份补丁恢复、依据是什么"这些知识以 commit 和 README 的形式留在了现场，而不是散落在某个人的记忆里。没有版本化的世界里，这种事故的标准处置叫"照着记忆重新写一遍"。

**行为审计从玄学变成查表。** 十几个自动化系统、三四个会自己改自己规则的 agent，某天你发现一条消息的语气不对，"谁改的"不再是问题——`git log -p` 五分钟定位到哪个深夜任务改了哪个提示词的哪一段、commit message 里为什么这么写。七天里像"追问消息的身份从用户改成 bot""链接从裸 URL 改成标题超链接"这类规则级变更，每一条都有完整的决策轨迹（决策人、日期、原因、涉及文件），全都可以回放。

**一次意外的安全审计副产品。** 建库推远端之前做全历史内容扫描，发现一份业务周报快照里躺着一把真实的 API 密钥——它进库时这个仓库还不存在，是历史数据被"第一次版本化"时照出来的。这类"你的数据比你以为的更敏感"的发现，后面还会再来两次（见摔跤记）。

**接手成本趋近于零。** 我们有过把仓库直接交给另一个新装实例理解的场景测试：clone、读 README、执行恢复三步——一个不知道这段历史前情的 agent，第一分钟就能看懂这套机制怎么运转。这大概是"给数据写文档"这件事第一次真正划算：文档的消费者不是人，是下一个 AI。

## 七天摔跤记：敏感信息三次误入库

这部分是这篇博客存在的真正原因。只讲收益的文章是软文，而 Git 对 agent 数据最有意思的性质恰恰是双刃的。

**第一次：历史里翻出密钥。** 就是上面说的，建库扫描发现周报快照带真 key。处置三件套：文件移出跟踪、`git filter-repo` 全历史重写（55 条 commit 映射，全部哈希变化、强推覆盖远端）、然后才是真正要紧的最后一步——去服务端轮换这把 key。一个反直觉的体会：**Git 让恢复变得容易，也让删除变得固执。**资产的每次改进和每次误入库，用的是同一套"忠实复制并永久留存"的机制。删除一个文件、清除一段历史、让凭据失效，是三件事，漏一步都不算完。

**第二次：清理过的东西第二天自己回来了。** 8 月底我们就把一类内部备份目录（208 个文件）移出过跟踪并写了 ignore 规则。规则写的是子目录路径，这个目录出现在另一个位置，没被罩住。更妙的是，我们自己的"每日快照自动全部提交"纪律忠实地把它们重新收了进来。ignore 不是历史橡皮擦，也不是内容分类器——自动化的提交纪律会放大边界上的每一个漏洞。

**第三次：健康检查脚本自己成了泄漏渠道。** 每天六点的例行体检里有一项"敏感内容扫描"，实现方式是遍历家目录。它遍历了什么范围？几乎全部——包括那份我们约定永不到处念的凭据配置。相当于我们安排了一个机器人，每天定时把最敏感的文件读进一个会被上报、可能被留存的上下文里。铁律被我们自己的守夜人违反了三个星期。修法：扫描器改成白名单目录遍历，被禁文件硬排除，并且把"扫描器不得越界"写成了测试。

三次事故，平均下来差不多两天一次边界修补。这是这类仓库的真实运维成本，任何教程不提这一段都是不诚实的。现在每天的检查里多了两条硬规矩：任何新文件入库前做内容级扫描（不看路径看内容）；自动提交的范围本身要过白名单。

## 这是长期机制，还是 Tricky 的 Hack？

我们的判断：**有纪律的外挂是正当架构，没纪律的外挂是定时炸弹。**

它"不像 Hack"的部分：不侵入运行时一行代码；Git 挂了 agent 照常工作，反过来也一样；模式有成熟先例（dotfiles、NixOS）；恢复路径可复现（README 里三条命令，实测过）；边界清晰（输入归 Git，状态归数据库协议，凭据归凭据系统）。

它确实还"Tricky"的部分：秘密的防线是 ignore 加自觉加事后扫描，没有密码学保底——私有仓库不是加密仓库，"private" 挡的是公开访问，不挡你自己的误操作；双仓库结构（代码一个库、数据一个库）的漂移要靠人和脚本守；commit message 的质量完全取决于写它的人（或 AI）的纪律。

什么信号出现时它该退休？官方把资产版本化做成协议的那天。这就引到最后一个问题。

## 官方路线图上有没有这个？有，而且有真重叠

我们翻了 [hermes-agent](https://github.com/NousResearch/hermes-agent) 的源码和公开 issue，结论比"官方没做"精确得多——**要分三块看**：

1. **已经交付、而且正好重叠一块：Profile Distribution。**最近版本里官方已经有"用 Git 仓库作为来源、发布安装一整套 agent profile"的机制——技能、配置、人格打包分发，接收方按清单安装，本机私有状态（记忆、会话、凭据）明确归属用户不被覆盖。这解决的是**分发**：把调好的 agent 安全地装到另一台机器/另一个人手里。我们仓库的"推远端、别人 clone"恰好撞了这条道的一部分，长期看资产发布该走它的协议。
2. **有代码但未普遍开放：Skill Sync**（跨设备技能同步），源码里在，但带预发布门控，不能当作"今天普通用户就能用"。
3. **确实还没做：本地资产的每次变更历史。**"技能写入即提交"是一个 open issue，未指派。官方把力气花在"恢复能力"上（备份、快照、checkpoint、回滚），我们要的"演化协议"（diff、blame、为什么改、选择性回退）仍然是空白。

所以三选一的裁决：**部分重叠——分发被官方覆盖了，版本化没有**。我们的方向不是拆掉这个仓库，而是让它瘦身分工：该走 Profile Distribution 的发布流出去走，本地仓库收敛为"受控资产源 + 演化历史"。这也是我们为什么给 README 写下"是否移动仓库、如何适配官方分发，在具体迁移任务里验收，不预设今天动"。

## 你要不要也做一个

如果你也在跑一个会自己写技能、改记忆的 agent，大脑超过二十个文件、有真实团队在用它，我的建议是做，成本一个下午。前提想清楚三件事：

- 把数据分三类：行为输入（进 Git）、运行事实（走数据库自己的备份）、凭据（内容扫描把门，永不进）
- 自动提交纪律先配好边界，再开自动化——否则你的 cron 会忠实地把错误方向的东西提交得又快又稳
- 接受它不保证什么：不能保证同 commit 重放出同一次对话（模型服务、检索、上下文都不在版本控制内），不能替代异地灾备，更不能当保险箱

真正让我觉得没做完的，是另一件事：文件进 Git 之后，agent 的**记忆**仍然没有语义版本。技能文件退回上周三是可行的；但"agent 对某个同事的判断""它对某个流程的理解"退回上周三，今天没有任何工具支持——记忆作为文本进了版本库，记忆作为认知，还活在每天的上下文压缩里，压过去就没了。

那一层什么时候会有自己的 Git？我们还没有答案。但方向我们是确定的。
