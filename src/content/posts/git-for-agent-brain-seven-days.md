上个月我写过一篇[《Agent 为什么也需要一套自己的 Git》](/posts/agent-native-git/)，论证一个长期自我改变的 agent 需要版本管理。那篇文章是一个想法。八月底之后它开始运转，七天后的现在，这篇是实战报告：既讲救过火，也讲摔过的跤。

先说清楚我们做了什么。没有重写任何东西，也没有装什么平台，就三步：在 agent 的数据目录执行一次 `git init`，写一份 `.gitignore`，推送到一个私有仓库。从此这个 agent 的技能、记忆、配置、脚本的每一次变化，都是一个带说明的 commit。

## 什么进仓库，什么永远不进

agent 的家目录里混着三类东西，边界必须划得干净。

第一类是它的"大脑"本身：技能文档（Markdown）、记忆文件、系统提示词、自动化脚本、定时任务配置。全部是纯文本，全部进 Git。七天里 2113 个文件进了版本库，其中技能占了九成。

第二类是运行状态：几百兆的会话数据库、日志、缓存。这些不进——数据库的行级变化塞进 Git 只会制造噪音，它们的备份走官方的一致性快照。这条边界一开始我们没划全，第一天就把心跳文件提交了两次，第二天清理掉。

第三类是凭据：密钥、token、登录态。永远不进。`.gitignore` 里写死，任何新文件进仓库前先做内容扫描。请记住这条，因为下面会有故事证明它有多容易失守。

## 为什么 Git 能无痛挂上去

这是被问最多的问题：一个跑着的产品，怎么就"外挂"了一个 Git，还不用改一行代码？

因为这类 agent 恰好同时满足三个条件。它的大脑是纯文本——不是存在数据库里的二进制，而是一个个 Markdown 文件；一个文件基本对应一个独立概念——一条技能、一段记忆，没有跨文件的事务依赖；文本和运行时是可分离的——agent 每次启动时才去读这些文件，Git 换掉文件的版本，agent 下次加载就是新大脑。

传统应用做不到，是因为状态活在数据库里。dotfiles 管理早就用同样的方式管 Linux 配置，我们只是意识到：新一代 agent 的"配置"就是它的记忆和技能，dotfiles 那套直接成立。

## 救火记录

七天里的数字：76 个 commit，日均十一次资产变更。这个密度下，Git 的价值不是理论。

最惊险的一次是升级踩踏。Hermes 官方升级把自己的代码仓库重置到上游，我们打在飞书适配层上的定制补丁被抹掉了。因为补丁以 commit 存在于 Git，`git reflog` 找回哈希、两条 `cherry-pick`，从发现到恢复完成 54 秒。要诚实地说明细节：真正救回源码的是代码仓库自己的 Git；外层数据仓库的价值，是把"恢复了什么、依据哪份补丁"留在了可审计的 commit 里。没有版本化之前，这类事故的标准处置是"照着记忆重新写一遍"。

还有一个更值钱的用途：行为审计。所有改动有作者、有日期、有说明——包括 AI 自己做的改动。某天发现一份文档的措辞不对，`git log -p` 直接定位到是哪一次任务改的、为什么改。对一个人来管理十几个自动化系统的团队，"谁改的"这个问题从玄学变成了查表。

## 摔跤记录

同一批七天里，边界事故发生了三次。

一次是净化历史时发现，某把 API 密钥随着某个周报快照进了仓库——那是建库之前的事，但 Git 不知道它"只是快照"。一次是 8 月底写好的 `.gitignore` 规则没覆盖根目录的新产物，第二天自动快照纪律忠实地把 208 个内部备份文件重新提交了上去。还有一次是一批任务台账导出落在 `tmp/` 目录，同样被"全部提交"的纪律带进了仓库。

这引出第一个反直觉的观点：**Git 让 agent 更容易恢复，也让秘密更难消失。**资产的每一次改进和每一次误入库，用的是同一套持久化和复制机制。误提交密钥后的标准处置是"历史重写"，那意味着全部 commit 哈希变化、强推覆盖远端——代价大、操作重，而且旧副本还在服务端缓存里滞留。删除一个文件、清除一段历史、让凭据失效，是三件事，都要做。

于是每天的例行检查里多了两条硬规矩：新增跟踪文件前先做内容级敏感扫描（不是看路径，是看内容）；扫描范围本身也要白名单化——我们一度让每天六点的健康检查脚本自己遍历了整个目录，等于安排了一个每天定时读敏感文件的机器人。检查者比被检查者更需要边界。

## 这是长期机制，还是 Tricky 的 Hack？

我的判断：**有纪律的外挂是正当架构，没纪律的外挂是定时炸弹**——而纪律本身可以自动化。七天之后我们给这个仓库配了自动体检（补丁完整性、敏感内容、重复事实三项每天跑）、远端私有镜像、恢复说明书放在仓库根目录（写给未来接手的新 agent 看的，它 clone 下来第一分钟就能读懂这套机制怎么运转）。

有意思的是官方路线和这件事的关系。最近的版本里，Hermes 已经把 Profile Distribution 做成了 Git 发布形态——官方开始用 Git 分发"一套 agent"。但它解决的是发布：技能怎么从一台机器安全装到另一台。本地这个仓库解决的是历史：这台机器上的大脑在过去七天变成了什么样、能不能退回某一天。分发和演化是两回事，短期内互补，长期看版本化可能会进官方协议，但今天它还是一个周末下午就能搭起来的旁挂方案。

## 你该不该做

如果你也在跑一个会自己写技能、改记忆的 agent，而且这些内容超过二十个文件，我会建议做，成本大约一小时。但有三个前提必须先想清楚：哪些文件是资产（进 Git）、哪些是状态（不进）、哪些是秘密（死都不进，且要靠内容扫描而不是靠自觉）；提交纪律要能坚持，或者干脆自动化；以及接受它的局限——Git 管得了文件，管不了会话数据库的一致性，那需要原生备份一起用。

真正让我在意的遗留问题是另一件事：文件版本化之后，agent 的"记忆"仍然没有语义版本。技能文件退回上周三是可行的；但"agent 对某件事的认知"退回上周三，没有工具支持。记忆作为文本进了 Git，记忆作为理解，还活在每天的上下文压缩里。那一层什么时候会有像 Git 一样的协议？现在没人知道。
