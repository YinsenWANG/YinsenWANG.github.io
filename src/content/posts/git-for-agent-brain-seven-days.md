你有没有遇到过这样的事：一个 AI 助理，教过它的东西，过几天又做错了；或者某天它说话的方式突然变了——你确定没人动过它的提示词。

那是它自己改的。

我们在团队里真跑着一个这样的 agent：Hermes（Nous Research 的开源项目），形态是一个常驻 gateway 进程加一个 CLI，通过飞书跟我们对话。它的"大脑"不是一段固定 prompt，而是家目录 `~/.hermes` 里一堆会生长的文件：**skills/** 两百多个技能目录，每个是一份 `SKILL.md` 工作说明书加自己的 references 和脚本——怎么发邀请邮件、怎么整理纪要、催办用什么语气，都是它自己写的；**memories/** 两个跨会话记忆文件；**SOUL.md** 人格定义；**config/** 各自动化流程的提示词与参数；**cron/jobs.json** 定时任务表。每天凌晨两点它跑批扫描团队群聊和会议纪要建任务台账，早上八点发日程简报，周一扫开源贡献者发邮件。这一个月里，它自己改这些文件的次数，比我们所有人加起来都多。

于是它成了一类很新的软件：**会自我改写，却说不清自己为什么变成现在这样。**改坏了没有"退回上周三"的按钮；行为突变找不到"是谁哪天改了什么"；两个 agent 各改各的，没法合并。

我们的解法说出来毫不起眼：**给它装了一台监控摄像头，加一台时光机。实现方式是一个 `git init`。**七天，76 个 commit。这篇讲透它为什么行、怎么装的、救过什么火、以及——更重要的——它让我们摔了什么跤。

## 先看清楚：agent 原生是怎么存数据的

不读源码就谈"给它加版本管理"是耍流氓。我们把它家目录翻了个遍，发现里面其实是**三个世界**，混住在一起：

**第一个世界：运行事实，活在 SQLite 里。**`state.db` 1.1 GB，schema 版本 30，三十来张表——`sessions` 管会话路由和压缩状态，`messages` 存每条消息和工具调用的配对，外加 FTS 全文索引（还有一套 trigram 索引管中文检索）、`compression_locks` 这种跨进程租约、`async_delegations` 记录后台委派任务的交付状态。开着 WAL 模式，主文件加 sidecar 才是一个完整时刻。官方为它配的保护相当讲究：`hermes backup` 生成的 ZIP 是**数据库感知**的——对每个 `.db` 走 SQLite 在线备份 API 拿事务一致副本，而不是复制正在写入的文件；升级前自动做快照，手工快照留 20 份、升级快照留 1 份，单文件超过 1 GiB 会跳过并在 manifest 里记账（我们实测最新两份升级快照就没有数据库文件，只有清单里一个 oversized 标记——**"存在快照"不等于"数据库有备份"**，这种坑只能读源码发现）。还有一个默认关闭的 Checkpoint 功能，看了实现会心一笑：底层就是一个影子 Git 库，每项目留 20 个恢复点。

**第二个世界：行为输入，就是散装文件。**上面说的那些技能、记忆、提示词、脚本——没有任何索引数据库管理它们的"内容"，agent 是扫描目录加载的（细节：技能发现有一层 30 秒 TTL 的缓存防抖，安装来源另有 `.bundled_manifest` 记录 hash 供升级比对；但文件的当前内容就是权威，这是关键性质）。官方对它们的保护是三样东西：完整 ZIP 备份捎带、技能整理器运行前 tar 一份技能树、以及那个可选的影子 Git。

**第三个世界：凭据。**`.env`、`auth.json`、各种 token。原生假设是你自己管好。

现在可以说清原生机制真正的缺口了——**不是"没有副本"，是副本不构成版本协议**。ZIP 和 tar 回答"某时刻保存了什么"；版本管理要回答：相对哪一版改了什么、为什么改、只退一个文件怎么办、两条改法怎么合、哪些机器该运行哪个版本。这五个问题官方一个都没答——issue 区里"技能写入即提交"的提案挂着，没指派。

## 为什么一个 git init 就挂得上

把 `~/.hermes` 变成 Git 仓库，不改它一行代码、不停服务、agent 对 Git 零感知。流行答案是"因为它的大脑是纯文本"——这只对了一半，GitHub 上被单个两兆 JSON 折磨的仓库多的是，文本性本身不值钱。

真正的条件有四条，我逐条对着源码核过：

**一、文件是"输入"而不是"状态"。**技能、提示词、规则是 agent 下次工作时读取的声明；消息、路由、租约是它工作产生的事实。声明可以版本化，事实要交给事务协议。这个区分就是整件事的物理学。

**二、加载语义没有跨文件一致性要求。**agent 读取技能时，不需要先问任何索引"这份文件的新版本生效了吗"——磁盘内容变了，下次加载就是新的。缓存、清单那些细节构成"刷新边界"（比如进行中的会话里，记忆是加载时冻结的快照，`git checkout` 不会让旧会话倒退——要下一个会话才生效），但不是"必须走官方 API 才认账"的一致性协议。外挂换文件，合法有效。

**三、变更频率和历史价值匹配。**一条技能一个月改两次，每次都是值得写进 commit message 的决策；state.db 一秒钟写十行，每行都留史等于灾难。

**四、文件边界接近语义边界。**一个技能目录≈一种能力，正文、参考文档、脚本一起评审一起回滚。

四条合起来是一条一般原理：**当系统的行为由低频、文本、文件即权威的声明驱动，运行事实另有可靠存储时，外挂版本层是自然设计。**dotfiles 社区二十年前就这么管 Linux 配置了——agent 不是发明了新模式，是把"配置即文本"的旧世界重新放大：配置变成了大脑。它的增量只有一样：改这些文件的不再是人，是它自己，频率高一个数量级，还不会写变更日志。

## 怎么装的：一个下午的工程量，三条生死线

```bash
cd ~/.hermes && git init
# 划边界（下面才是正事）
git remote add origin git@github.com:<you>/hermes-home.git  # 私有
```

`.gitignore` 是这个方案里最重要的文件，比所有 commit 加起来都重要。三条线：

- **资产进库**：`skills/`、`memories/`、`SOUL.md`、`config/` 下的提示词与参数、`scripts/`、cron 的任务定义。最终 2113 个文件，技能占九成
- **状态不进**：`state.db*`（连 WAL sidecar 一起排）、`logs/`、`cache/`、`state-snapshots/`、会话导出
- **凭据死都不进**：`.env*`、`auth.json*`。而且很快你会发现只看路径不够，必须补内容级扫描——先记住这句，下面有事故现场

纪律三条：改资产前后各 commit 一次；commit message 写人话带因果（真实例子：`tracker: 追问一律改用 bot 身份（不再以某人名义发言，09-04 指正）`）；每天凌晨跑批收尾自动快照一次。**然后给仓库写一份 README，是写给"未来接手这个目录的任何人或任何 AI"的**：这是什么、边界在哪、恢复三步（`git log` 找基线 → `git show <commit>:<path>` 取文件 → 跑完整性体检脚本）、哪些东西永远不该进来。这条当时觉得最虚，七天后我们认为它最值——因为接手的第一候选，就是一台新机器上全新安装的 agent 自己。

配套自动化两件：**每日六点的健康检查**（补丁完整性 + 敏感内容扫描 + 数据单一来源扫描，红灯直接发飞书）；**升级前钩子**（核对定制补丁的恢复材料在不在位）。

## 时光机显灵的三个现场

**54 秒的复活。**9 月 4 日下午官方升级（那版本一次推进几百个 commit），把内层代码仓库 reset 到上游，我们在飞书适配层打的两个定制补丁一夜蒸发——那里面是晨报卡片的拦截逻辑和勾选并发锁，丢了它们整个自动化简报就瘫了。因为补丁以 commit 存在：`git reflog` 翻出 reset 前那两个哈希，两条 `cherry-pick`，reflog 时间戳显示从 reset 到补丁回库相差 54 秒，体检脚本确认五个 marker 全部就位。诚实说清两点边界：54 秒是仓库内窗口，发现—验证—重启服务的全流程更长；而且这一局救火靠的是代码仓库自己的 Git——外层数据仓库的角色，是把"该用哪份补丁、按什么顺序 apply、恢复完跑什么验收"写成 README 和版本化 patch 文件留在现场。**没有版本化之前，这类事故的标准处置叫"照着记忆重新写一遍"。**

**行为审计从玄学变成查表。**七天里有一条真实的规则演化链，全在历史里躺着：任务催办消息原来是裸 URL，某次指正"太啰嗦"，`git log -p` 能看到 runbook 从 `--text 裸链接` 改成 `--markdown [标题](链接)` 的那一行 diff、改的日期、和 commit message 里写的指正原因；紧接着另一条消息把发送身份从"以用户名义"改成"以 bot 名义"——两条改动隔着几小时，各自独立可回放，谁哪天以什么理由改了什么，三岁小孩都能查。放以前这叫"我记得好像是……来着？"

**最意外的一用：commit message 成了 agent 的外置长期记忆。**我们要求自动化任务的收尾 commit 写人话，跑了一阵发现，新开的会话读家目录时会把 `git log` 当材料——它能知道"自己上周为什么改了催办语气"。一个为人类设计的机制，顺手治好了机器的失忆症。这大概会成为一个标准件：agent 的长期记忆，一半在 memory 文件里（该记住的），一半在版本历史里（做过什么决定的完整流水账）。

## 同一批七天，摔跤三次

只讲收益的文章都是没挨过打的文章。版本化对 agent 最有意思的性质是双刃的，三起事故按时间排：

**第一跤：历史里翻出活密钥。**建库扫描时，发现一份周报运行产物里躺着一把真实 API key——它在建库之前就躺在目录里，Git 一进来就忠实地把它变成"永久历史的一部分"。处置三件套：`git rm --cached`、`git filter-repo` 全历史重写（55 条 commit 映射、全部哈希变化、强推覆盖远端、GitHub 后台 GC 慢慢清缓存副本）——然后才是真正要紧的最后一步：**去服务端轮换这把 key**。这里藏着本篇最重的一条经验：**Git 让恢复变得容易，也让删除变得固执。**资产的每次改进和每次误入库，用的是同一套"复制并永久留存"的机制；路径删除、历史清除、凭据作废是三件事，做两件等于没做。

**第二跤：清掉的东西第二天自己复活。**一类内部备份（208 个文件）我们移出过跟踪、也写了 ignore 规则——但规则写的是 `skills/.curator_backups/`，这批东西躺在根目录 `.curator_backups/`，路径没罩住。更讽刺的是把我们再坑一把的，恰恰是我们自己的纪律："每日跑批收尾全部提交"的自动化忠实地把这批漏网文件重新收了进来并推送。**ignore 不是橡皮擦，也不是分类器；自动化的提交纪律会把边界的每一条缝隙认真放大。**修法是把扫描从"看路径"升级成"看内容"：任何将入库的新文件先过一遍凭据形态扫描（密钥正则、业务数据结构），而不是信任目录名。

**第三跤：守夜人自己越界。**每天六点的健康检查里有一项数据扫描，实现是遍历家目录找重复事实。它遍历了什么？几乎全部——包括那份我们立了铁律"任何 AI 不得读取"的敏感配置。相当于雇了个机器人，每天定时把禁区文件读进一个会上报的上下文，持续了三周才被发现（外部独立审查抓的）。修复是双层的：扫描器改白名单目录遍历，硬排除清单写死在代码里；**并且给"扫描器不得越界"本身写了测试**——负向用例：往禁区放一个探针文件，扫描器要是报告了它，体检直接失败。检查者比被检查者更需要边界，这条现在写在 README 里。

三跤摔完，这个仓库的安全模型才算成型：路径排除 → 内容扫描 → 白名单遍历 → 越界测试，四层里每一层都是前一层的事故换来的。你问我值不值——那把 key 如果在建库那天没照出来，它今天就在某个远端仓库的历史里裸奔。

## 所以，这是架构还是 Hack？

**有纪律的外挂是正当架构，没纪律的外挂是定时炸弹**——而纪律恰好都能自动化：内容扫描、白名单、每日体检、越界测试、README 里的恢复手册。把这五件事配齐，这个一个下午搭起来的旁挂方案就可以当长期基础设施用。

它也有体面的退路。翻 hermes-agent 的仓库会发现这条路不是旁门：官方最近的版本里有 **Profile Distribution**——用 Git 仓库作为来源发布安装整套 agent profile，本机私有状态明确归用户；还有一个 **Skill Sync**（跨设备技能同步），源码已在、带预发布门控；issue 区"技能写入即提交"挂着未指派。官方的力气在"分发"和"恢复"，本地资产的"演化历史"仍空白。所以我们的裁决是**部分重叠**：将来资产发布那半该迁去走官方协议，仓库瘦身为"受控资产源 + 演化历史"——方向是收敛，不是拆除。

如果你也在跑一个会自己写技能、改记忆的 agent，大脑超过二十个文件、团队真的靠它干活，建议做，一个下午的事。三个前提照抄我们的学费：行为输入和运行事实分开管；自动提交纪律先配好内容扫描再开闸；接受 Git 管不了的部分——它不能保证同一个 commit 重放出同一场对话，更不能当保险箱。

最后留一个我们没解决、今天也没有任何工具能解决的问题：**文件能回滚，理解不能。**技能退回上周三是 `git checkout` 的事；但"agent 对某个流程的认知"退回上周三——记忆作为文本进了版本库，记忆作为认知还活在每天的上下文压缩里，压过去就没了。版本化的下半场，是给"理解"做 Git。

那是下一台时光机的事。
